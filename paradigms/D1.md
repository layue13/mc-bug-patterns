# D1 多视图状态不同步

**一句话**：同一份物品/库存状态有两个可写视图（界面槽位、方块实体、物品数据、网络对端），其中一个被改动或销毁后，另一个仍可操作，物品因此出现在两处。

**机理**：界面打开时读取一份引用或快照，真正的数据在别处被修改（别的玩家、拆除、传送、死亡、下线、替换底层存储），而写回只发生在"关闭界面"这一个时机，或根本没有校验底层对象是否还是同一个。

**读代码时找什么**
- 界面/菜单的有效性判断恒为真，或只检查距离，不检查底层对象是否仍存在、是否被替换。
- 以物品为后端的容器：只在关闭时写回；两个界面可同时指向同一物品。
- 菜单持有的存储对象在其生命周期内可能被换成别的对象（如拔出存储介质、更换配置）。
- 玩家下线、换槽、丢弃载体物品时，界面状态是否被安全地丢弃或结算。
- 载体物品能否被**备用输入路径**移走：副手交换键、数字键、丢弃键、其他模组的快速移动。只拦住鼠标点击是不够的。
- 读取方的更新早于被读取对象的变更（事件/更新顺序），导致读到旧值后又被覆盖。

**确认条件**（全部满足）
1. 能指出两个可写视图，以及它们各自的写入点。
2. 能写出一条外部操作序列，让两个视图在没有同步的情况下都保留了物品。
3. 界面的有效性判断或写回逻辑确实没有拦住这条序列。

**排除条件**
- 界面只读，没有可取出的槽位。
- 后端是界面私有的临时容器，关闭时只结算一次且不复制。
- 有统一的所有权/锁机制，并且在取物前校验。

**典型修法**（专门修复模组里反复出现的四种）
1. 有效性判断里校验**身份**：方块实体——确认世界里该位置的方块实体仍是同一个对象，再判断距离；物品——确认玩家手里仍是同一件物品。
2. **排他使用**：同一个共享容器同时只允许一个玩家打开，第二个被拒绝。
3. **状态一变就关界面**：切换快捷栏槽位、下线、手持物变化、丢弃载体物品时强制关闭。
4. **拦截交换键**：对载体物品的"交换/热键"点击直接忽略。
另外：槽位变化即时落盘。

**证据强度**：强。MC百科 17 条；一个专门修复复制漏洞的模组里有约 17 个补丁属于这几种修法（多个互不相关的模组中的同类容器：工作台类、背包类、箱子类、工具锻造台等，读过实现）；AE2 的 issue 中有"界面打开期间用副手交换键移走宿主物品"（读过正文）、"更新早于变更"（读过正文，原因未确认）。**静态规则基本无法确认**，需要构造并发操作序列或读完整个生命周期。
