# D1 多人/并发 GUI 状态不同步 → 复制
规则：`mc-d1-menu-always-valid`、`mc-d1-item-backed-menu-saves-on-close-only`

## 判定目标
同一份物品状态是否存在两个可写视图（界面槽位 vs 方块实体/物品 NBT），且另一个玩家/事件能在两者之间插入修改。

## 必须读的代码
命中的 Menu 类全文 + 它对应的 BlockEntity/Item 类 + 注册它的 `MenuProvider`/GuiHandler。

## 确认条件（confirmed 需全部满足，并写出 trigger_path）
1. 槽位后端是 **共享可变对象**（BlockEntity 库存、物品 NBT 反序列化出的 handler），不是界面私有副本。
2. 存在使该对象被改动/移走/销毁/传送的外部路径（拆方块、掉落、传送器、另一玩家打开同一物品/方块、死亡、登出），而 `stillValid`/`removed` 没有拦截。
3. 界面关闭或继续操作时，**旧视图被写回或仍可取物**，导致两边都有物品。
- `stillValid` 恒为 true 只是线索：若 Menu 绑定的是 BlockEntity 且有 `isRemoved()` 或距离检查在别处（如 `slot.mayPickup`）→ 重新判断。

## 排除条件（false_positive）
- 菜单是纯客户端展示或只读（没有可取出的槽位）。
- 后端是 Menu 私有 `SimpleContainer`，关闭时一次性返还玩家，且返还前未复制。
- 项目有统一的 `ContainerLocker`/所有权令牌并在 `stillValid` 中校验（引用该代码）。

## 需要人工（needs_human）
无法确定 Menu 的另一端（BlockEntity/Item）是否在本仓库内，或依赖其他模组的事件（传送器、搬运类）。

## 建议修法
槽位变化即时写回；`stillValid` 校验方块存在/物品身份/距离；登出时强制关闭容器；对物品背包使用 UUID 并拒绝同一 UUID 同时被两个 Menu 打开。

## 对应站点案例
末影之手(101)、箱子宝宝(120)、传送器(144)、采花袋(121)、饰品盒(122)、私人箱子(117)、信件(175)。
